Mozaik centers on one idea: **everything the model sees and produces should be modeled as structured context**, not loose strings scattered across your codebase.

## Context

A **`Context`** is the full ordered history (and metadata) the model needs for the next inference step. You:

- Create it with an id meaningful to your app (session, project, thread).
- Append **input** items (user/developer messages, tool results, ...).
- After each model call, **output** items (assistant content, tool calls, reasoning, ...) are appended so the thread stays consistent.

This makes multi-turn flows, branching, and replay easier than pushing raw strings through every layer.

```ts
import {
  Context,
  DeveloperMessage,
  UserMessage,
  InMemoryContextRepository,
} from '@mozaik-ai/core';

const context = Context.create('project-id')
  .addItem(DeveloperMessage.create('You are a helpful assistant.'))
  .addItem(UserMessage.create('What is the capital of France?'));

const repo = new InMemoryContextRepository();
await repo.save(context);

const restored = await repo.getByProjectId('project-id');
```

## ContextItem

A **`ContextItem`** is one atomic piece of that history. Concrete item types are aligned with the [OpenResponses](/docs/open-responses) vocabulary.

### Client items (you add these)

| Item | Purpose |
| --- | --- |
| `UserMessage` | End-user text (or structured content). |
| `DeveloperMessage` | Developer / system instructions. |
| `FunctionCallOutput` | Result of executing a tool after the model requested a `FunctionCall`. |

### Model items (appended by the loop)

| Item | Purpose |
| --- | --- |
| `ModelMessage` | Assistant-facing message content produced by the model. |
| `FunctionCall` | A tool invocation requested by the model. |
| `Reasoning` | Opaque or structured reasoning segments when the provider exposes them. |

Together, these items form an ordered transcript you can persist, trim, or transform.

## How it fits into the agent loop

During a run, the [agent loop](/docs/agent-loop) calls the provider with the current `Context`. Any model-produced items are appended back onto the same `Context` your app owns, so by the time `agent.run(...)` resolves, the context is ready to:

- Persist via a `ContextRepository`.
- Feed into the next turn.
- Share across multiple agents in an [`AgentSociety`](/docs/agent-society).

You rarely need to call `applyModelOutput` yourself unless you are driving inference outside the loop via [`OpenAIResponses`](/docs/open-responses) directly.

## Persistence

A **`ContextRepository`** defines how contexts are stored and loaded (e.g. **`InMemoryContextRepository`** for tests and demos). Implement the interface against Postgres, Redis, or object storage so you can `save` after each turn and `getByProjectId` (or similar) when a user returns.

## Generative model types

Around inference, Mozaik exposes:

- `GenerativeModel`, `InferenceRequest`, `InferenceResponse`.
- `Tool` — declare callable capabilities for the model.
- Token usage helpers: `TokenUsage`, `InputTokenDetails`, `OutputTokenDetails`.

Call sites stay typed end-to-end from tool declaration through inference response.
